# Implementation Sub-plan: Foundation Hardening and ICP Persistence

This document is an implementation checklist, not a competing release. Its work belongs to Feature 0 (`v0.0-foundation`) and Feature 1 (`v0.1-icp`).

## Feature 0 Work

1. Add tenant, user, account, session, campaign, sequence, enrollment, scheduled-action, approval, and audit persistence as required by the shared domain contract.
2. Establish validated tenant context for each request and require it in tenant-aware repositories.
3. Configure transaction-scoped PostgreSQL RLS for all tenant-owned tables. Policies must fail closed when tenant context is absent.
4. Implement account lease tokens, atomic acquisition, heartbeat, expiry recovery, and ownership checks.
5. Implement atomic budget reservation, commit, release, and reservation identity.
6. Persist audit events with actor, tenant, entity, action, before/after data, correlation ID, payload hash, and test-data marker.
7. Add PostgreSQL concurrency tests. In-memory tests may support unit behavior but cannot satisfy database acceptance criteria.

## Feature 1 Work

1. Persist ICP definitions, import batches, prospects, and evaluation history with tenant-scoped foreign keys and indexes.
2. Canonicalize LinkedIn URLs before duplicate detection and use database `ON CONFLICT` behavior for concurrent imports.
3. Persist validation, deterministic-filter, AI-evaluation, and manual-review outcomes separately.
4. Use a provider interface for AI and a fake provider in automated tests. Record model, prompt version, schema version, evidence references, and validation result.
5. Make imports resumable with row-level progress, idempotency keys, failure state, and safe retry behavior.
6. Keep qualification separate from `READY_FOR_CAMPAIGN`; human approval is required for readiness.
7. Provide an exportable approved audience and a minimal API/UI only after persistence behavior is verified.

## Migration Policy

- Edit `src/db/schema.ts` first.
- Generate a reviewed Drizzle migration.
- Test it against a fresh local PostgreSQL database and a representative existing state.
- Do not use destructive `db:push` or drop-table scripts for shared or production data.
- Record any manual RLS migration steps in the migration documentation.

## Completion Check

Feature 0 and Feature 1 are complete only when their canonical feature plans pass. This sub-plan is complete when all listed implementation tasks are either implemented and linked to tests or explicitly deferred in the owning feature plan.
