# RecruitmentOS 0.8: Competitor & Influencer Post-Engager Sourcing

**Plan ID:** `0.8-competitor-influencer-post-engager-sourcing`  
**Classification:** Medium feature. Adds Channel 5 using the existing OpenCLI, prospect, engagement-draft, and `scheduled_actions` paths.  
**Status:** Revised after Tushar's decisions. Planning only; this does not authorize code edits, migrations, browser automation, or live LinkedIn actions.

---

## Goal

Add **Channel 5: Competitor & Influencer Post-Engager Sourcing** for RecruitmentOS sales/product users.

For selected, active competitor or influencer targets, Channel 5 will discover recent LinkedIn posts, extract public likers and commenters, qualify their visible profile information, and store each qualified engager as a normal prospect. It will then automatically scan that prospect's recent posts, produce one contextual comment and one like recommendation, and use the existing autonomous approval-to-`scheduled_actions` path to queue the warm-up actions.

The channel must operate like Channels 1-4: it is a sourcing input into the existing prospect and engagement workflow, not a separate lead-management or queueing system.

## Confirmed Decisions

1. **Native queue only:** `scheduled_actions` plus `ActionQueueService` remains the sole action queue and worker. The existing server auto-drain cadence (`AUTO_DRAIN_GAP_MS = 300_000`) is reused. No BullMQ/Redis queue, warm-up queue table, second drainer, or competing scheduler.
2. **Channel alignment:** Channel 5 follows the same injected-runner/channel-orchestrator pattern as Channel 4's `ContentSearchChannel` and `OpenCliContentSearchRunner`.
3. **Fully autonomous:** qualified Channel 5 prospects do not wait for `promoteProspect` or a manual review. The Channel 5 orchestration explicitly transitions them to the ready stage, records the system decision/audit event, creates engagement drafts, and relies on the existing `autoApproveAndQueueCycle` to enqueue them.
4. **Prospect persistence:** use the existing `prospects` table and `customAttributes`, with the existing canonical LinkedIn URL upsert rule. Do not create attribution, run, target-post, or warm-up relational tables.
5. **Target registry:** seed Bullhorn, Loxo, Ashby, HireEZ, Greg Savage, Hung Lee, Lou Adler, Adam Karpiak, The Elite Recruiter Podcast, Benjamin Mena, and Michael Quinn Alexander. Operators can select/deselect each target using an active/inactive toggle.

## Assumptions And Non-Goals

### Assumptions

- An authenticated OpenCLI LinkedIn session is available for Channel 5, as it is for Channel 4.
- The existing account defaults, engagement controls, daily budgets, kill switch, cooldown checks, idempotency protections, and auto-approval cycle are configured for autonomous engagement.
- Seed records require reviewed canonical LinkedIn URLs before production use. The requested names alone are insufficient to safely navigate a profile/company feed.
- Current uncommitted source and migration work is intentional and must be preserved. This plan is an untracked planning-document update only.

### Non-goals

- No new LinkedIn provider, credential handling, proxying, CAPTCHA bypass, or bulk-crawling platform.
- No manual promotion or a Channel-5-specific approval screen.
- No new queue, queue worker, queue status model, or bespoke queue UI.
- No separate provenance/attribution schema. Source data remains in the prospect's `customAttributes`, matching the existing channels.
- No changes to Channel 1-4 behavior, queue drain semantics, or action-safety services except the smallest integration needed for Channel 5 to invoke their existing public paths.

| OpenCLI boundary | `OpenCliContentSearchRunner` uses `open` -> page ID -> wait -> `extract` -> pure parser, with runner injection for offline tests. | Build `OpenCliPostEngagerRunner` in the same style for target feed/post/engager extraction. |
| Prospect storage | `prospects` has `(tenant_id, normalized_linkedin_url)` uniqueness and JSON `custom_attributes`. | Post scan and drafts | `EngagementService.scanProspect` uses the configured `ProspectPostSource` to ingest recent prospect-authored posts. `createLikeRecommendation` creates the deterministic LIKE draft; existing comment-draft generation creates the contextual comment draft. | After a Channel 5 prospect becomes ready, invoke this existing scan/draft flow. ## User Journeys

### Configure targets

1. A sales/product operator opens Channel 5 in the discovery UI.
2. The registry offers the predefined targets. Each row shows target name, target type, LinkedIn URL, and an active toggle.
3. The operator can activate or deactivate individual targets. Inactive targets are excluded from sourcing without deleting historical prospects.
4. The operator starts Channel 5 for all active targets or an explicitly selected subset.

### Source, store, and warm up an engager

1. Channel 5 opens each selected target's recent LinkedIn activity using OpenCLI, then obtains recent post URLs.
2. For each post within the request cap, it extracts public commenter and reactor entries: profile URL, name, visible headline/interests, interaction type, and comment text when rendered.
3. The channel rejects malformed/non-profile URLs and applies the same qualification policy used by the other sourcing channels for recruitment sales prospects.
4. It normalizes the profile URL and upserts the prospect in `prospects`. New prospects receive Channel 5 metadata in `customAttributes`; existing prospects retain their stage and existing custom data while gaining non-destructive Channel 5 source metadata.
5. A qualified Channel 5 prospect is moved to `READY_FOR_CAMPAIGN` by the explicit autonomous system path, with `review_decisions` and `audit_events` recording `system-channel-5` as the actor and why it qualified.
6. The channel calls `EngagementService.scanProspect` to retrieve the prospect's own recent posts. For an eligible post it creates/reuses a like draft and creates/reuses a contextual comment draft through the existing engagement service/provider path.
7. `autoApproveAndQueueCycle` approves pending drafts and invokes `requestAction` for each. `requestAction` writes idempotent LIKE and COMMENT rows to `scheduled_actions` only after its existing safety checks pass.
8. `runAutoDrainCycle` drains the native queue at its existing five-minute cadence. All resulting action statuses remain observable through the existing queue and engagement UI.

### Empty and failure paths

- An inactive target is skipped; an all-inactive request returns `NO_ACTIVE_TARGETS`.
- No recent source posts or no valid engagers yields a completed result with zero qualified prospects, not an error.
- An engager with no eligible recent post becomes ready but produces no warm-up draft/action; return a recorded `NO_ELIGIBLE_PROSPECT_POST` outcome.
- Session, OpenCLI, extraction, qualification, draft, or safety failures are surfaced as structured codes. They must never fabricate prospects, drafts, or queued actions.
- A disabled control, exhausted budget, active kill switch, cooldown, expired session, duplicate post comment, or uncertain prior execution is handled by existing `requestAction`/queue behavior and prevents unsafe enqueueing.

## Data, API, And Frontend Contract

### Entities And Database Approach

| Entity | Storage | Required fields/constraints |
| --- | --- | --- |
| Target registry | One small tenant-scoped `engagement_target_sources` registry table, if no suitable existing configuration table can represent target type, canonical LinkedIn URL, and `is_active`. | `id`, `tenant_id`, `target_type` (`COMPETITOR` or `INFLUENCER`), `display_name`, `linkedin_url`, `normalized_url`, `is_active`, timestamps; unique `(tenant_id, normalized_url)`, indexed `(tenant_id, is_active)`. |
| Prospect | Existing `prospects` table. | Existing unique `(tenant_id, normalized_linkedin_url)` governs dedupe. `customAttributes` stores Channel 5 metadata. |
| Prospect-authored warm-up post | Existing `engagement_posts`. | Insert through the existing `scanProspect` path and post-identity dedupe. |
| Like/comment recommendations | Existing `engagement_drafts`, revisions, and approvals. | Existing draft/post action uniqueness and revision validation apply. |
| Queued action | Existing `scheduled_actions`. | Insert only through `EngagementService.requestAction`; existing idempotency key and comment-slot protections apply. |

Only the registry is new persistence. Do not add `post_engager_runs`, `target_source_posts`, `prospect_source_attributions`, or `prospect_warmup_queue`.

**Migration:** if the registry cannot use an existing generic configuration table after implementation-time inspection, add one forward additive Drizzle migration after the in-flight `0008`/`0009` work is reconciled. Use UUID `tenant_id`, add it to `src/db/rls.sql`, and test tenant isolation. Seed data is applied idempotently by a service/API call rather than hard-coded in a migration, allowing each tenant's selected/inactive state to persist. Never alter historical migrations or recreate `prospects`/`scheduled_actions`.

### `customAttributes` Contract

For a new Channel 5 prospect, merge the following compatible metadata with existing standard attributes:

```ts
{
  name: string,
  title: string, // public headline when available
  source: 'COMPETITOR_INFLUENCER_POST_ENGAGER',
  sourceTarget: string,
  sourceTargetType: 'COMPETITOR' | 'INFLUENCER',
  sourceTargetUrl: string,
  sourcePostUrl: string,
  sourceInteraction: 'LIKE' | 'COMMENT',
  sourceCommentText?: string,
  sourceObservedAt: string,
}
```

For an existing prospect, do not overwrite manually curated `name`, `title`, source data from a different channel, or its lifecycle stage. Preserve the first source fields and append/update a bounded `channel5Sources` evidence list only when the existing JSON convention can support it. The implementation must define and test an explicit bounded/truncation policy so repeated engagement extraction does not grow JSON without limit.

### API Contract

Routes use existing request tenant/operator/correlation middleware. Request bodies never carry tenant or operator IDs, and errors use `structuredRefusal`.

| Method | Path | Request | Success | Key errors |
| --- | --- | --- | --- | --- |
| `GET` | `/api/discovery/engager-targets` | `?active=` | `{ targets, correlationId }` | `TENANT_FORBIDDEN` |
| `POST` | `/api/discovery/engager-targets/seed` | none | `{ created, existing, targets, correlationId }` | `SEED_FAILED` |
| `PATCH` | `/api/discovery/engager-targets/:id` | `{ isActive }` | `{ target, correlationId }` | `TARGET_NOT_FOUND`, `TARGET_INVALID` |
| `POST` | `/api/discovery/post-engagers` | `{ targetIds?: string[], recency?: 'past-24h' | 'past-week' | 'past-month', maxPostsPerTarget?: number, maxEngagersPerPost?: number }` | `{ status, counts, prospects, correlationId }` | `DISCOVERY_INVALID`, `NO_ACTIVE_TARGETS`, `SESSION_UNAVAILABLE`, `EXTRACTION_FAILED`, `DISCOVERY_FAILED` |

Use conservative caps aligned with Channel 4's input-validation style. The response reports target/post/engager/qualified/duplicate/filtered/no-eligible-post counts and sanitized per-target errors. It must not expose DOM payloads, raw OpenCLI output, session data, tab IDs, or browser stderr.

### Frontend Contract

Extend the existing discovery interface using the `DiscoveryPanel` conventions rather than a separate operational dashboard:

- A Channel 5 section/tab lists the 11 seeded targets grouped by competitor/influencer, including active/inactive toggles and a seed action for an empty tenant registry.
- A sourcing control selects active targets, recency, maximum posts per target, and maximum engagers per post.
- Results show source target, interaction type, prospect name/headline, profile link, source post link, and outcome: stored, duplicate, filtered, no eligible prospect post, draft created, or queued through the native queue.
- Render idle, loading, no-active-targets, completed-empty, completed, partial, session-unavailable, and API-error states from server results. Do not present a manual Promote or separate warm-up queue control for Channel 5.

## Acceptance Criteria

1. Each tenant can idempotently seed the 11 requested targets; re-seeding does not duplicate or reactivate a target set inactive by an operator.
2. Only active selected targets are sourced; inactive and unknown target IDs cannot be run.
3. Channel 5 uses an injected OpenCLI runner with the Channel 4 `open` -> wait -> extract -> pure-parser pattern, and all automated tests remain offline with no OpenCLI process spawn.
4. Valid public engagers are deduplicated through the existing canonical `(tenant_id, normalized_linkedin_url)` prospect identity. Invalid URLs never create prospects.
5. New prospects contain required Channel 5 source metadata in `customAttributes`; existing prospect stages and non-Channel-5 custom attributes are not overwritten.
6. Qualified Channel 5 engagers autonomously reach `READY_FOR_CAMPAIGN`, with a system review decision and audit event. They never require an operator promote click.
7. Each eligible qualified prospect is scanned through `scanProspect`; the flow produces/reuses one like and one contextual comment draft for an eligible recent prospect post, subject to existing post/draft idempotency.
8. Channel 5 does not directly insert into `scheduled_actions`. The existing `autoApproveAndQueueCycle` and `requestAction` create the scheduled LIKE/COMMENT actions, which the existing `ActionQueueService` drains under the existing five-minute cadence and safety controls.
9. Session, parsing, no-target, no-engager, no-eligible-prospect-post, disabled-control, budget, cooldown, duplicate, uncertain, and action-execution outcomes are explicit and never reported as a fabricated success.
10. API responses are tenant scoped, validated, sanitized, and free of raw browser/session/DOM data; UI covers idle, loading, empty, completed, partial, and failure states.
11. `npm run typecheck` and the full `npm test` suite pass; all Channel 1-4, engagement, action-queue, adapter, and DiscoveryPanel regressions remain green.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| LinkedIn DOM changes or session failure | Isolate selectors/parsers in the injected runner; return structured failures; never synthesize engager data. |
| Automated LinkedIn writes | Keep all writes within existing draft approval, control, budget, cooldown, account-health, comment-slot, idempotency, lease, and queue-drain protections. |
| Metadata growth in JSON | Define a small bounded source-evidence list and preserve first/most-recent source values; test truncation. |
| Seed URL correctness | Treat reviewed canonical URLs as a release blocker; do not guess handles/slugs. |
| Existing global queue backlog | Channel 5 joins the existing queue by design. UI must describe queued status, not predict execution time. |
| Existing auto-drain paired-action behavior | Do not alter it in this feature. Verify the Channel 5 action order and actual behavior against current queue tests; any cadence-policy change requires a separate approved plan. |

## Rollback Notes

1. Set all registry targets inactive to stop further Channel 5 sourcing without touching existing prospects or native queue processing.
2. Disable/remove only the Channel 5 route/UI registration to stop new intake; existing queued actions continue through the established queue lifecycle and can be handled using existing queue controls.
3. Prefer deactivation over deleting sourced prospects or historical `customAttributes` evidence.
4. If a registry migration exists, it is additive. Roll back application behavior first; only drop the registry table after confirming no tenant still needs its configuration or history. Do not roll back shared prospect, engagement, or queue tables.
