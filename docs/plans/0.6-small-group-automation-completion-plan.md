## 1. Goal and Binary Completion Contract

### Business result

Deliver a controlled Small Group -> Automation workflow that lets an authorized operator qualify ICP prospects, prepare campaign-ready engagement, draft and revise likes/comments, approve a specific revision, and then use a durable simulated, manual, or separately enabled supervised browser action path. The business value is trustworthy operator decision support and tightly controlled action execution, not autonomous outreach volume.

### Operator journey and visible outputs

1. The operator creates an ICP, imports prospects, reviews deterministic/provider qualification evidence, and explicitly changes eligible prospects to `READY_FOR_CAMPAIGN`.
2. The operator uses fixture/manual post intake by default, reviews provenance, canonical target URL, author/prospect association, eligibility, hash, and cooldown/refusal information.
3. The operator creates a Like or Comment recommendation, reviews evidence and validator results, and edits only by creating a new immutable revision. Approval is tied to exactly that revision and expires or is invalidated when its content, target hash, policy, or eligible state changes.
4. The operator sees separate Like and Comment controls, approval state, pilot allowance, account health, working-hours decision, budget/cooldown result, queue/manual-task state, and audit/evidence references from server responses.
5. The operator requests `SIMULATE`, `MANUAL`, or a separately enabled `BROWSER` mode. The UI never converts a local request into a successful result without authoritative server state.
6. A manual action creates a durable `pending` task. Only an explicit authorized completion records `manual-confirmed`; failures and uncertainty do not become success.
7. A supervised browser run is one action at a time, visible, target-verified before the write, and checked after the write. A successful write path is `browser-executed` until independently verified; unclear external state is `uncertain` and is never retried automatically.

Allowed outcome/status vocabulary across API, persistence, audit, and UI:

| Label | Meaning |
| --- | --- |
| `pending` | Awaiting approval, queue claim, manual confirmation, or another explicit transition; not an external success. |
| `simulated` | Fake executor/fixture result only; no LinkedIn write attempted. |
| `manual-confirmed` | An authorized operator recorded a completed manual action; it is not browser independently verified. |
| `browser-executed` | The supervised browser completed its write path but verification has not established the resulting external state. |
| `verified` | The expected target and action result were verified, with redacted evidence/audit correlation persisted. |
| `uncertain` | A possible write cannot be proven or disproven; automatic retry is prohibited. |
| `refused` | A policy, tenant, approval, budget, cooldown, lease, health, idempotency, or kill-switch check blocked the request before a write. |
| `failed` | A confirmed non-success failure occurred without claiming an unproven external action. |

### Binary completion contract

Completion is **YES** only when every required workstream and verification rung in this plan has recorded evidence. In particular:

- trusted operator/tenant context is server-derived, and all tenant-owned reads/writes occur under repository predicates plus the RLS transaction context;
- migrations, RLS, queue claiming, leases, budgets, idempotency, controls, revisions, and manual tasks are proven in isolated PostgreSQL tests rather than inferred from memory doubles;
- Like and Comment are independently enabled, approved, budgeted, cooled down, kill-switched, audited, and tested;
- every execution result is durable and labeled using the vocabulary above, with browser success never presented as `verified` without verified external state;
- the UI displays server truth and all material refusal/error/uncertainty states with no seed/demo fallback or optimistic success; and
- live migration and LinkedIn rungs are explicitly approved and run separately. Unperformed live rungs are `NOT RUN`, not passed.

Otherwise completion is **NO**. Current worktree code, including the previously repaired engagement slice, is not completion evidence by itself.

## 2. Scope, Assumptions, and Non-goals

### REQUIRED

- ICP/prospect qualification, campaign-readiness separation, engagement drafting, human approval, supervised Like/Comment execution, durable persistence, and an operator web UI.
- A 4-5 total-action pilot maximum, performed only one at a time after a separate approval. Scaling requires a fresh decision based on pilot evidence.
- Likes and comments remain independently enabled and independently approved.

### Assumptions

- `APPROVED_DEV_DATABASE_TARGET` is the only approved development PostgreSQL target. Its value is sensitive and is neither accessed nor reproduced by this plan.
- Authenticated LinkedIn browser profile use was previously approved for supervised development/testing only. No browser or live action is authorized in this planning turn.
- External AI/provider use was previously approved in principle, but no provider is called in planning. Provider data minimization and retention remain a review decision.
- Production auth is absent from the inspected server. The smallest acceptable interim boundary is explicit development-only authenticated middleware that resolves a fixed, server-owned operator/tenant identity outside request bodies; it must be isolated behind an interface replaced by production authentication later, and must fail closed when absent.

### Non-goals

- Connections, messages, follow-ups, sequences, profile changes, stealth behavior, CAPTCHA/checkpoint circumvention, multi-account/unattended operation, automatic scale-up, and a claim of legal/platform compliance.
- Environment, credential, MCP, or other operational-configuration changes.
- Applying migrations, calling providers, opening browser profiles, or running LinkedIn actions under this plan.

## 5. Contracts, Entities, Permissions, and Failure States

### REQUIRED domain entities and constraints

- **TrustedRequestContext:** `tenantId`, `operatorId`, authorization role/capabilities, request correlation ID. It is generated by authentication middleware and never accepted from request JSON.
- **EngagementPost:** tenant/prospect, canonical URL, immutable ingestion provenance/hash/text snapshot, author identity, publication timestamp, eligibility decision/reasons. Enforce unique `(tenant_id, canonical_post_url)`.
- **RecommendationRevision:** immutable action type, post hash, comment content where applicable, evidence, validator report, creator, lifecycle state, and predecessor/version. Enforce unique `(tenant_id, recommendation_id, revision)`.
- **RecommendationApproval:** binds one operator, revision, action type, policy-version/expiry, and state. Enforce at most one active approval for a revision/action type; invalidation is an append-only state transition/audit event.
- **EngagementControl:** independent Like/Comment enablement, action-specific cooldown/working-hours policy, tenant/account/action scope, and global/tenant/account/action kill-switch evaluation.
- **ScheduledAction:** tenant/account/prospect/revision/post hash/action/mode/payload hash, semantic idempotency key, status, claim token/heartbeat reference, refusal/error code, outcome label, and terminal timestamp. Enforce semantic idempotency by tenant/account/revision/action/mode/payload hash, not only the current global key.
- **BudgetReservation and AccountLease:** tenant/account/action/day reservation state; one token-bound lease per tenant/account with heartbeat, expiration, stale-token rejection, and safe recovery.
- **ManualTask / ExecutionEvidence / AuditEvent:** durable task linked to a scheduled action, terminal confirmation actor/time/redacted metadata, and append-only correlation of request, approval, claim, executor, verification, health, and stop events.

### Permissions and API contract

- All server routes resolve context through trusted middleware. No `tenantId`, `operatorId`, account authorization, approval, or policy decision comes from the request body.
- Development-only identity has the narrow explicit boundary in Section 2; it cannot be enabled implicitly in production and cannot grant cross-tenant/operator access.
- Preserve existing ICP/import/prospect/export paths, but return structured error objects: `{ status: 'refused' | 'failed' | 'pending', code, message, correlationId, currentState? }`.
- Additive engagement contract: intake/list/review/revision approval/action request/manual-task outcome/action history/control and health read routes. Browser-specific worker/run/stop routes remain unavailable while Feature 0.5 is disabled.
- Machine-readable refusal/failure codes include `AUTH_CONTEXT_REQUIRED`, `TENANT_FORBIDDEN`, `PROSPECT_NOT_READY`, `POST_NOT_ELIGIBLE`, `APPROVAL_REQUIRED`, `APPROVAL_EXPIRED`, `APPROVAL_INVALIDATED`, `ACTION_DUPLICATE`, `COOLDOWN_ACTIVE`, `BUDGET_EXCEEDED`, `LEASE_UNAVAILABLE`, `STALE_LEASE_TOKEN`, `KILL_SWITCH_ACTIVE`, `WORKING_HOURS_CLOSED`, `ACCOUNT_PAUSED`, `SESSION_EXPIRED`, `CHECKPOINT_DETECTED`, `WRONG_TARGET`, `SELECTOR_MISMATCH`, `RATE_LIMITED`, `EXECUTION_TIMEOUT`, `EXECUTION_UNCERTAIN`, `MANUAL_CONFIRMATION_PENDING`, and `PROVIDER_UNAVAILABLE`.
