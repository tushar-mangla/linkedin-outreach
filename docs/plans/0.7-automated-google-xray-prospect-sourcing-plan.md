# RecruitmentOS 0.7: Automated Google X-Ray Prospect Sourcing

**Plan ID:** `0.7-automated-google-xray-prospect-sourcing-plan`  
**Classification:** Large/risky feature. It introduces an external search-provider boundary, new prospect provenance/persistence, automated qualification and engagement preparation, a React workflow, and an existing supervised browser-write capability.  
**Status:** PROPOSED. This document authorizes planning only. It does not authorize application edits, migrations, live Google/DuckDuckGo searches, browser sessions, LinkedIn activity, provider calls, credential/configuration changes, or a production rollout.

## 1. Business Outcome and Operator Workflow

### Goal

Replace manual prospect entry and CSV import as the normal RecruitmentOS acquisition path with a controlled, evidence-backed discovery flow for founder-led specialist or boutique recruitment agencies. An operator starts one discovery run from the Prospects tab; the system finds public LinkedIn profile results through ICP-derived Google X-Ray searches, deduplicates them, qualifies them through the existing ICP pipeline, prepares eligible prospects for engagement, and keeps the final external Like/Comment decision and action supervised.

### Target ICP

- Agency type and size: founder-led specialist or boutique recruitment agencies, approximately 5-50 employees.
- Target titles: Founder, Managing Director, Commercial Director, Head of Business Development, Managing Partner.
- Target niches: Tech, Engineering, Finance, Life Sciences, Executive Search.
- Evidence/pain themes for qualification and drafting: founder burnout, inconsistent lead flow, referral dependence, and feast-or-famine pipeline.
- Disqualifiers: high-volume/low-margin temporary staffing and generalist agencies.
- Baseline query shape: `site:linkedin.com/in/ ("Founder" OR "Managing Director" OR "Managing Partner") ("recruitment" OR "executive search") ("tech" OR "engineering" OR "finance" OR "life sciences")`.

### User journey

1. The operator creates or selects the RecruitmentOS ICP, including target titles, niches, geography/location terms, positive pain/problem signals, and exclusions.
2. On the **Prospects** tab, the operator clicks **Discover ICP Prospects**, optionally selects an existing ICP and locations, and sees the generated query summary before the run starts.
3. The server creates a discovery run, queries the configured public HTML-search adapter within a strict page/result/time budget, parses only public result title/snippet/URL data, canonicalizes LinkedIn profile URLs, and reports progress and counts.
4. The server suppresses invalid, non-profile, and already-known canonical LinkedIn URLs. It records source/query/result provenance without storing whole search-result pages.
5. Newly discovered prospects enter `PersistentIcpPipeline`; deterministic disqualifiers run first, then the existing AI evaluator scores remaining candidates. The operator sees discovered, duplicate, filtered, evaluated, review-required, rejected, and error counts.
6. The operator reviews qualified/requires-review prospects and explicitly promotes an appropriate prospect to `READY_FOR_CAMPAIGN`. Discovery or AI scoring never grants campaign readiness by itself.
7. For a ready prospect, the existing `ProfileActivityPostSource` (when separately browser-enabled) or fixture source discovers recent posts. `EngagementService` filters posts and produces grounded comment/like recommendations using the stored ICP evidence and pain themes.
8. The dashboard shows the prospect, qualification evidence, post/provenance, draft, validation findings, controls, and action outcome. The only external-action decision is the operator choosing **Approve Like** or **Approve Comment** for a specific recommendation revision.
9. The existing supervised Playwright executor performs only the approved action in a visible browser. Unverified or unclear outcomes are displayed as `uncertain`; no automated retry or success claim occurs.

### Non-goals

- Removing CSV/manual intake in this release; those remain a fallback and regression path.
- Bulk crawling LinkedIn, profile-page scraping during search acquisition, credential collection, CAPTCHA/checkpoint bypass, proxy rotation, multi-account operation, or unattended LinkedIn actions.
- Automatic campaign readiness, approval, likes, comments, connections, messages, follow-up sequences, or scale-up beyond the separately approved supervised pilot.
- Claims that Google, LinkedIn, or another provider permits this workflow. Provider terms, robots, privacy obligations, and local legal requirements remain operational review responsibilities.

## 2. Binary Completion Contract and Acceptance Criteria

**Completion is YES only if every item below is implemented and has the stated test evidence. Otherwise completion is NO.** A UI button, a successful HTTP response, or a browser click alone is not completion evidence.

1. An authorized operator can start an additive `Discover ICP Prospects` run from the Prospects tab for a selected tenant-owned ICP, with validated optional location constraints and an explicit bounded result/page budget.
2. The server builds deterministic X-Ray queries from the saved criteria plus RecruitmentOS defaults; generated queries contain the LinkedIn profile site restriction, at least one included title/niche clause when configured, and never include raw credentials or client-supplied tenant/operator identity.
3. The search adapter parses mocked public HTML into only valid `linkedin.com/in/` prospects. It extracts name, headline/title, company when inferable, location when inferable, canonical profile URL, and source evidence. Missing fields are represented as empty/unknown evidence rather than invented facts.
4. Each discovery run records terminal state and count reconciliation: `resultsSeen = accepted + duplicates + invalid + rejectedByParser`; pipeline counts reconcile separately. A rate-limit, blocked page, malformed HTML, timeout, or provider failure is `failed`/`partial`, never a successful empty run.
5. Canonical URL deduplication works both inside a run and against the tenant-scoped `prospects` unique constraint. Duplicate results create no duplicate prospect/evaluation and do not overwrite operator-maintained attributes or stage.
6. Accepted discovery results use `PersistentIcpPipeline` (not a parallel scoring path): deterministic exclusions precede AI evaluation, evaluations/audit records retain source provenance, and only an explicit review route can set `READY_FOR_CAMPAIGN`.
7. Ready prospects flow into the existing post-discovery, drafting, approval, and supervised-execution chain. The new discovery feature neither weakens post eligibility nor bypasses action approval, controls, budget/cooldown, browser flag, verification, or uncertainty handling.
8. The UI exposes idle, validating, running/progress, completed, partial, refused, rate-limited, and failed discovery states; it refreshes only from server responses and clearly reports discovered/new/duplicate/qualified/review-required counts.
9. Offline unit, ingestion, API/UI integration, and regression tests pass without external search or LinkedIn access. Any separately approved live smoke test is recorded as `NOT RUN` until actually performed and cannot substitute for offline evidence.

## 4. Architecture and Contracts

### 4.1 Google X-Ray sourcing architecture

Introduce an explicit, testable discovery module under `src/services/icp/` rather than embedding scraping logic in Express routes or `PersistentIcpPipeline`.

1. **`IcpProspectDiscoveryService`** orchestrates one tenant/ICP-scoped run: validate options, load criteria, build bounded query variants, call the search adapter sequentially, parse/normalize/dedupe results, persist provenance/dispositions, and hand only accepted prospects to the persistent pipeline.
2. **`XrayQueryBuilder`** converts `IcpCriteria` plus RecruitmentOS defaults into deterministic query variants. Titles and niches use quoted OR groups; locations produce separate bounded query variants rather than an unbounded cartesian expansion. Apply a maximum query count, maximum character length, and max results/pages per run. Use hard-coded RecruitmentOS disqualifier terms only as deterministic pipeline criteria unless a reviewed query exclusion improves precision without hiding legitimate profiles.
3. **`HtmlSearchClient`** is an interface, not a browser automation dependency. It receives a query, page/cursor, timeout, and correlation ID and returns `{ provider, requestUrl, status, body, receivedAt }`. Initial implementation uses direct HTML fetch with a stable, truthful application user agent and explicit request pacing. A provider implementation may target Google HTML only where its use is approved; a DuckDuckGo HTML adapter can be a reviewed fallback when Google is blocked. Neither adapter may solve CAPTCHAs, use proxy pools, rotate identities, log cookie/session data, or bypass access controls.
4. **`XrayResultParser`** consumes the client response and returns typed candidates/discards. It accepts result links only when URL parsing produces `https://www.linkedin.com/in/<handle>` (normalization removes query/fragment/trailing slash according to the existing normalizer). It extracts public display title/snippet and derives name/headline/company/location conservatively; ambiguous values remain blank with source evidence, not fabricated.
5. **`DiscoveryDeduplicator`** suppresses duplicate canonical URLs in memory before pipeline work, then checks tenant persistence. The database unique index remains authoritative. A duplicate disposition must identify `within_run` vs `existing_tenant`; do not update an existing prospect's stage, review decision, or curated data merely because it reappeared in search.
6. **Source-aware pipeline ingestion** creates a discovery source batch with `sourceType: GOOGLE_XRAY` (or approved fallback provider), immutable query/parser metadata, and counts. It invokes existing deterministic evaluation and AI scoring. Store source fields in `customAttributes` only as a transitional compatibility detail; durable relational provenance is the target data model.
7. **Progress/reporting** has a durable run ID. The initial synchronous implementation must obey a bounded server timeout and publish phase/count updates; if the budget cannot finish within it, return/retain `PARTIAL` and resume only through an explicit operator command. Do not claim background processing unless a durable worker/queue is introduced and tested.

### 4.2 Entities, database, and migration approach

Preserve existing `prospects`, `import_batches`, `icp_evaluations`, `review_decisions`, and `audit_events`; do not overload CSV filename semantics as the sole search evidence.

| Entity | Required data and constraints |
| --- | --- |
| `prospect_discovery_runs` | Tenant ID, ICP definition ID, source type/provider, requested options (including locations), query-plan hash, run status (`CREATED`, `RUNNING`, `COMPLETED`, `PARTIAL`, `FAILED`, `REFUSED`, `RATE_LIMITED`), started/completed time, bounded count fields, sanitized failure code/message, correlation ID. Tenant/index status and creation-time indexes required. |
| `prospect_discovery_queries` | Run ID, ordinal, normalized query text/hash, provider request identity, attempt/page, status, result count, started/completed time, response metadata safe to retain. Unique `(run_id, ordinal, attempt)` or reviewed equivalent prevents duplicate accounting. |
| `prospect_discovery_results` | Run/query ID, source rank, raw/canonical profile URL, title/snippet evidence or hash, parsed name/title/company/location, parser version, disposition (`ACCEPTED`, `DUPLICATE_IN_RUN`, `DUPLICATE_EXISTING`, `INVALID_URL`, `NON_PROFILE`, `PARSER_REJECTED`, `PIPELINE_REJECTED`), linked prospect ID when created/resolved. Unique `(run_id, canonical_profile_url)` for canonical rows. |
| `import_batches` | Add a source discriminator and nullable discovery-run link only through a forward migration if needed for pipeline compatibility. Maintain CSV compatibility and historical rows. |

Use a new forward Drizzle migration and metadata snapshot. It must add tenant RLS/policies consistently with the current repository's security model, foreign keys/indexes/check constraints, and a reversible down/operational rollback description. Never rewrite existing uncommitted migration history or drop/recreate `prospects`. ### 4.3 API contract

All routes derive tenant/operator/correlation from `requestContextMiddleware`; request bodies never set identity.

**Proposed additive routes:**

- `POST /api/icps/:icpDefinitionId/discoveries`
  - Request: `{ locations?: string[], maxQueries?: number, maxResultsPerQuery?: number }` with strict server caps; no free-form arbitrary query in v0.7.
  - Success `202`/`201`: `{ runId, status, phase, queryCount, resultsSeen, accepted, duplicates, invalid, pipeline: { processed, evaluated, filteredOut, requiresReview, rejected }, correlationId }`.
  - Refusal/error: `{ status: 'refused' | 'failed' | 'partial' | 'rate_limited', code, message, runId?, retryAfterMs?, correlationId }`.
- `GET /api/icps/:icpDefinitionId/discoveries/:runId`
  - Returns server-authoritative phase/status, bounded progress/counts, query summary, sanitized error/retry information, and result dispositions. It never returns raw HTML, cookies, provider tokens, or hidden result metadata.
- `GET /api/prospects` remains additive-compatible. Extend its DTO deliberately with optional discovery summary/provenance only if UI needs it; preserve fields used by the existing Prospects/Review/Engagement views.

Routes must validate ICP ownership/activity, source provider enablement, input sizes, and concurrent-run policy. Concurrent clicks for the same ICP should return the active run or an explicit `DISCOVERY_ALREADY_RUNNING`, not create parallel provider traffic. Use machine-readable codes including `ICP_INVALID`, `ICP_NOT_FOUND`, `DISCOVERY_ALREADY_RUNNING`, `DISCOVERY_BUDGET_EXCEEDED`, `SEARCH_RATE_LIMITED`, `SEARCH_BLOCKED`, `SEARCH_TIMEOUT`, `SEARCH_RESPONSE_INVALID`, `SEARCH_PROVIDER_UNAVAILABLE`, `DISCOVERY_PARTIAL`, and `PIPELINE_INGESTION_FAILED`.

### 4.4 Frontend contract

Update the existing **Prospect Qualification Pipeline** panel in `src/App.tsx`:

- Add a compact discovery control group above manual add: selected ICP, optional location input/chips constrained by the selected ICP, result budget summary, and **Discover ICP Prospects** button.
- Disable duplicate submission while a run is active; show phase-specific progress and reconciled counts: queries completed/total, results seen, new, duplicate, invalid, filtered, evaluated, review-required, and rejected.
- On completion/partial/failure, retain server status and expose a retry only after the server-declared backoff. Refresh prospects from `/api/prospects`; do not synthesize candidate rows locally.
- Display a source/provenance marker and qualification disposition in prospect/review detail. For a ready prospect, keep existing engagement controls and render post/draft/recommendation/approval states. **Approve Like** and **Approve Comment** must remain separate commands bound to one revision and must not be implied by discovery completion.
- Preserve manual add and CSV tabs as explicit fallback paths. The UI must handle empty state, validation refusal, no configured ICP, rate limit, blocked search, timeout, parser-zero-result, duplicate-only result, partial completion, pipeline/provider failure, and API unavailability without optimistic success.

### Platform/provider and privacy risks

| Risk | Required mitigation and failure behavior |
| --- | --- |
| Google HTML rate limiting/blocking | Strict per-run query/page/result budget, sequential pacing with jitter, exponential backoff, `Retry-After` honor, server-side cooldown, and `SEARCH_RATE_LIMITED`/`SEARCH_BLOCKED` status. Do not convert it to an empty successful run. |
| User-agent rotation/evasion | Do **not** rotate user agents, proxies, IPs, accounts, or fingerprints to evade detection. Use one stable, truthful application UA where permitted. The plan interprets the requested UA-rotation review as an explicit rejection of evasive rotation. |
| Search-result markup volatility | Version parsers, retain only minimal sanitized evidence, fixture-test known HTML variants, classify unparseable output, and provide a reviewed provider-neutral fallback. Never infer a person/company from arbitrary text. |
| Query amplification/cost | Cap query variants, pages, results, total run duration, retries, and active runs per tenant/ICP. Require explicit operator initiation for every run in v0.7. |
| Data accuracy and duplicate identity | Treat snippets as leads, not verified profile facts; canonicalize URL, preserve source evidence and parser confidence, do not overwrite curated data, and require existing review before campaign readiness. |
| LinkedIn and external-action boundary | Discovery consumes search-result HTML only. Direct profile activity retrieval and any write stay behind existing feature flags, visible Playwright supervision, approval/controls, target verification, and uncertainty semantics. No credential/session data is in discovery records/logs. |
| Privacy/retention | Store minimal source text/hash and query metadata; no raw HTML, cookies, session data, full result pages, or secrets. Define a reviewed retention/deletion period before rollout. |
