# RecruitmentOS ICP Engagement And Supervised LinkedIn Execution Gap Plan

**Plan identifier:** `0.5-recruitmentos-icp-supervised-execution-gap-plan`
**Release target:** `v0.5-supervised-execution`
**Classification:** Large/risky feature planning: external browser writes, authenticated sessions, tenant isolation, approval state, concurrency, budgets, retries, and auditability.
**Plan status:** Proposed. This planning change does not modify application code.

## 1. Business Outcome And Concrete Workflow

RecruitmentOS should let a recruiter move from an explicit RecruitmentOS ICP to a qualified prospect, discover recent LinkedIn posts with provenance, produce an evidence-grounded comment recommendation, review and approve a like or comment, and execute exactly that approved action in a visible LinkedIn browser under a controlled account. The recruiter must be able to see what happened, stop the run, recover from a session or page-state problem, and use a manual fallback without the system claiming an external action succeeded when its result is uncertain.

Primary workflow:

1. The recruiter defines or selects an ICP using the existing criteria schema and imports prospect data.
2. The ICP pipeline applies deterministic exclusions before model evaluation, stores qualification evidence, and routes borderline prospects to review.
3. The recruiter approves a prospect for campaign readiness. This approval does not approve a LinkedIn like or comment.
4. The recruiter scans the approved prospect using fixture/manual discovery in Feature 0.2, or the supervised visible browser discovery capability delivered here after explicit enablement.
5. RecruitmentOS stores the canonical post URL, author, text, publication time, source, content hash, and discovery evidence; recency, quality, blocklist, duplicate, and cooldown rules produce an explainable eligibility state.
6. A provider creates a structured like/comment recommendation. The recruiter reviews the source post, evidence, draft, validation findings, and policy status, then approves, edits and approves, rejects, skips the author, or pauses the prospect.
7. For an approved action, the operator chooses `FAKE`, `MANUAL`, or `PLAYWRIGHT` only when that capability is enabled. The system rechecks tenant ownership, approval revision, eligibility, cooldown, lease, working hours, kill switches, and action-specific budget immediately before dispatch.
8. The visible Playwright browser opens the authenticated LinkedIn profile/session, verifies the target post and current UI state, performs one like or comment, verifies the resulting external state, captures redacted evidence, and records success, failure, or uncertainty.
9. The operator can stop the run at any point. Session expiry, checkpoint/CAPTCHA, selector mismatch, timeout, rate limit, or uncertain outcome pauses the account and prevents automatic retry. Manual execution remains available where policy permits.

## 3. Exact Scope, Non-Goals, Assumptions, And Phases

### Scope

- Preserve the existing ICP qualification and Feature 0.2 preparation workflow.
- Complete durable approval/revision/action state needed to authorize live execution.
- Complete queue persistence, atomic claims, lease tokens/heartbeats, action-specific budgets, cooldowns, retries, idempotency, and audit records.
- Add a typed fail-closed safety gate and account health/kill-switch controls.
- Add a visible, persistent-profile `PlaywrightExecutor` for one controlled LinkedIn account.
- Execute only approved likes and comments in the first live pilot; each capability must be independently enabled.
- Add API/UI controls for review, supervised run status, stop, health, manual fallback, and uncertain outcomes.
- Test offline, isolated database, controlled browser fixtures, and one explicitly approved live validation path.

### Non-goals

- No unattended, stealth, parallel, scaled, or multi-account automation.
- No connection requests, messages, follow-ups, profile edits, sequence orchestration, reply automation, analytics, or campaign enrollment changes.
- No bypass of LinkedIn authentication, CAPTCHA, checkpoint, rate limit, or platform controls.
- No automatic retry after an uncertain external write.
- No provider rollout, secret/configuration setup, or data-sharing decision without approval.
- No claim that a live action works until the explicit live validation gate passes on the approved test account.

### Assumptions

1. Feature 0.2 preparation remains usable with fixture/manual discovery and Fake/Manual execution even when live execution is disabled.
2. A prospect must be tenant-owned and `READY_FOR_CAMPAIGN` before engagement discovery or recommendation scheduling.
3. A recommendation approval is bound to an immutable content revision and post content hash; edits supersede prior approval.
4. The initial deployment is single-user, but tenant and operator identity remain explicit and trusted server-side.
5. Only one browser worker owns one LinkedIn account lease at a time.
6. LinkedIn UI selectors are versioned fixtures and may fail; failure is safer than guessing.
7. PostgreSQL is the source of truth for durable execution; memory storage is for offline tests only.

### Phases

| Phase | Outcome | Gate |
| --- | --- | --- |
| 0. Baseline and migration reconciliation | Resolve current schema/migration drift and establish isolated PostgreSQL/PGlite test strategy | No implementation proceeds on unexplained migration state; dirty worktree is preserved |
| 1. Preparation contract hardening | Make ICP, discovery, drafting, review, approval revisions, and manual fallback durable and tenant-safe | Feature 0.2 preparation acceptance remains green with browser writes disabled |
| 2. Queue and safety foundation | Complete durable action claim, approval enforcement, leases, budgets, cooldowns, idempotency, kill switches, and audit | Offline and isolated DB gates pass; no external browser writes enabled |
| 3. Controlled browser surface | Implement Playwright session/account abstraction, selector fixtures, page-state verification, redaction, and execution evidence | Controlled browser fixture suite passes; live capability remains disabled by default |
| 4. Supervised like pilot | Enable one approved account and one approved like at a time, with visible browser and stop controls | Tushar explicitly approves authenticated profile, account, like policy, limits, and live validation |
| 5. Supervised comment pilot | Enable comments separately with edited/approved content, stronger verification, and manual fallback | Tushar separately approves comment capability, content posture, limits, and live validation |

## 4. User Journeys And State Contract

### Required journeys

- ICP creation/import/qualification/review/export with deterministic exclusions, AI evidence, and tenant isolation.
- Approved prospect to fixture/manual post discovery, eligibility explanation, evidence-grounded draft, edit/review, and manual completion.
- Approved like: review post, approve like, acquire account lease, pass safety checks, run visible browser, verify liked state, persist result and audit.
- Approved comment: review source evidence and exact text, approve or edit, run visible browser, verify comment appears or mark uncertainty, persist result and audit.
- Failure: selector mismatch, login redirect/session expiry, checkpoint/CAPTCHA, timeout, rate limit, network failure, or browser crash pauses the account and leaves no false success.
- Duplicate prevention: repeated approval, queue request, worker retry, or API replay returns existing semantic action/result and performs at most one external attempt.
- Manual fallback: when browser execution is disabled or blocked, create a durable manual task; task creation is not external success; the operator records `COMPLETED`, `FAILED`, or `UNCERTAIN` with confirmation metadata.
- Kill switch: tenant/account/action/global stop prevents new claims and interrupts the current supervised run at the next safe checkpoint; all stops are audited.

### State dimensions

- Prospect qualification/readiness: existing ICP stages; do not conflate with engagement or execution.
- Post eligibility: `ELIGIBLE`, `REVIEW_REQUIRED`, `NOT_ELIGIBLE`, with rule/evidence details.
- Recommendation revision: `DRAFT`, `PENDING_REVIEW`, `APPROVED`, `REJECTED`, `SUPERSEDED`, `PAUSED`.
- Scheduled action: existing `PENDING`, `CLAIMED`, `COMPLETED`, `FAILED`, `UNCERTAIN`, plus explicit `CANCELLED`/`BLOCKED` if needed for operational reporting.
- Manual task/result: `PENDING_CONFIRMATION`, `COMPLETED`, `FAILED`, `UNCERTAIN`, `EXPIRED`.
- Account health: `HEALTHY`, `WARNING`, `PAUSED`, `CHECKPOINT_DETECTED`, `REAUTH_REQUIRED`, `DISABLED`.
- Kill switches: independent global, tenant, account, and action-type controls.

## 5. Entities, Permissions, And Contracts

### Entities and invariants

| Entity | Required fields/invariants |
| --- | --- |
| `icp_definitions`, `prospects`, `icp_evaluations`, `review_decisions` | Preserve existing schema; every query and mutation is tenant scoped; deterministic hard exclusions cannot be overridden by model evaluation. |
| `engagement_posts` | Tenant, prospect, canonical post URL, author key/profile URL, text, published time, source type, content hash, evidence/provenance, eligibility decision; unique `(tenant_id, canonical_post_url)`. |
| `engagement_recommendations` and revisions | Tenant, post, prospect, action type, immutable revision/content hash, evidence references, generated/edited text, provider metadata, validation report, state; approval binds to revision/hash. |
| `engagement_approvals` | Tenant, recommendation/revision, operator, decision, reason, timestamp, supersession; approval is required at dispatch and cannot be accepted from the request body alone. |
| `engagement_cooldowns` | Tenant, account/prospect/author scope, action type, start/end, origin, and result; like and comment are independently configurable. |
| `scheduled_actions` | Tenant, prospect, account, action type, recommendation/revision reference, payload hash, scheduled time, claim fields, status, semantic idempotency key; one external attempt per semantic key. |
| `account_leases` | Tenant/account unique ownership, worker, cryptographic lease token, expiry, heartbeat; release/heartbeat must validate token. |
| `daily_action_budgets` and `budget_reservations` | Tenant/account/action/day key; reservation and counter update are transactional and action-specific. |
| `browser_sessions` | Tenant/account, encrypted profile/session reference or key version, browser mode, last verified time, health, operator, no raw credentials in payload/logs. |
| `execution_evidence` and `account_health_events` | Tenant, action/session, redacted screenshot/HTML metadata or hashes, selector version, state verification, error class, timestamps, operator. |
| `manual_execution_tasks` and `action_results` | Tenant, scheduled action/recommendation, instructions, outcome, confirmation metadata, executor mode, external evidence, uncertainty reason. |
| `kill_switches` | Scope and action type, enabled state, reason, actor, timestamps; fail closed and audited. |

Permissions for the current single-user deployment use the trusted server operator and tenant context. Future role names require approval. The API must not accept arbitrary `tenantId`, `accountId` ownership, or operator identity as authorization from a client body.

### API contract

Retain existing Feature 0.1/0.2 endpoints and add typed validation/error mapping. Proposed routes:

- `GET /api/icps`, `POST /api/icps`, `POST /api/imports`, `POST /api/imports/:id/process`, `POST /api/prospects/:id/review`: preserve existing contract; add durable response/error behavior and no optimistic UI success.
- `POST /api/engagement/scan`: preserve fixture/manual preparation; add explicit source mode and bounded timeout; live source is Feature 0.5-only and must be capability-gated.
- `GET /api/engagement/posts`, `GET /api/engagement/recommendations`, `POST /api/engagement/recommendations/:id/decision`: return evidence, revision, validation, approval, cooldown, and eligibility state without cross-tenant records.
- `POST /api/engagement/recommendations/:id/actions`: request `{ accountId, mode: 'FAKE' | 'MANUAL' | 'PLAYWRIGHT', idempotencyKey }`; server derives tenant/operator, verifies approval/revision and safety predicates, and returns queued/blocked/duplicate state.
- `POST /api/scheduled-actions/:id/process` or a worker entry point: requires worker identity and lease token; claims exactly one action and returns `COMPLETED`, `FAILED`, or `UNCERTAIN` without exposing secrets.
- `POST /api/manual-tasks/:id/outcome`: accepts only a terminal explicit outcome and confirmation metadata; already-terminal tasks return conflict.
- `GET /api/execution/accounts/:id`, `POST /api/execution/accounts/:id/session/verify`, `POST /api/execution/accounts/:id/stop`, `POST /api/execution/kill-switches`: expose health, session verification, stop, and kill-switch controls to an authorized operator.
- `GET /api/execution/audit`: bounded tenant-scoped audit/evidence history with redacted payloads.

Error codes must include `ICP_INVALID`, `PROSPECT_NOT_READY`, `TENANT_ACCESS_DENIED`, `POST_DUPLICATE`, `POST_NOT_ELIGIBLE`, `APPROVAL_REQUIRED`, `APPROVAL_STALE`, `ACTION_DUPLICATE`, `COOLDOWN_ACTIVE`, `BUDGET_EXCEEDED`, `LEASE_UNAVAILABLE`, `KILL_SWITCH_ACTIVE`, `ACCOUNT_PAUSED`, `SESSION_EXPIRED`, `CHECKPOINT_DETECTED`, `SELECTOR_MISMATCH`, `RATE_LIMITED`, `EXECUTION_TIMEOUT`, `EXECUTION_FAILED`, `EXECUTION_UNCERTAIN`, `MANUAL_CONFIRMATION_PENDING`, and `PROVIDER_UNAVAILABLE`. Responses must be sanitized and machine-readable.

### Executor contract

Preserve `LinkedInExecutor` in `src/executors/types.ts`; extend `ActionResult` only additively with executor mode, external verification state, error classification, evidence references, and uncertainty reason. `PlaywrightExecutor` must:

- accept an injected browser/session/account context and selector version rather than reading arbitrary credentials from action payloads;
- run headed by default for pilot actions and expose current step/stop state;
- verify login/session before action, target post identity before write, and external state after write;
- use bounded navigation/action timeouts and no blind selector retries;
- classify login redirect, checkpoint/CAPTCHA, rate limit, selector mismatch, timeout, browser crash, and uncertain verification separately;
- redact cookies, tokens, authorization headers, profile paths, and raw page secrets from logs/audit payloads;
- close pages/contexts and release leases in `finally`, while retaining durable outcome evidence.

## 8. Binary Completion Contract And Acceptance Criteria

The release is complete only if every item is true:

- [ ] ICP criteria can be created, persisted, applied deterministically before AI evaluation, reviewed, and used to identify `READY_FOR_CAMPAIGN` prospects with evidence and tenant isolation.
- [ ] A ready prospect can receive a fixture/manual post or explicitly enabled supervised discovery record with canonical URL, author, text, date, provenance, content hash, and explainable eligibility.
- [ ] A recommendation can be generated, quality-validated, reviewed, edited, rejected, skipped, or paused; approval is mandatory and bound to the exact revision/content hash.
- [ ] Like and comment are separate action types with separate enablement, budgets, cooldowns, policy checks, audit events, and acceptance tests.
- [ ] Fake and Manual modes execute through the same queue contract; Manual task creation remains pending until explicit outcome confirmation.
- [ ] Playwright execution uses one visible browser/account lease, verified session, versioned selectors, page-state verification, bounded timeouts, redacted evidence, and explicit success/failure/uncertain result.
- [ ] No unapproved, stale, invalid, duplicate, cross-tenant, ineligible, cooldown-blocked, budget-exhausted, lease-invalid, kill-switched, paused-account, checkpointed, or session-expired action can reach an external write.
- [ ] A provider timeout, rate limit, browser timeout, selector mismatch, session expiry, checkpoint/CAPTCHA, or browser crash produces a durable non-success state, account health transition as appropriate, and no automatic retry for uncertainty.
- [ ] Semantic idempotency prevents duplicate action creation and duplicate external attempts across API replay, worker retry, process restart, and concurrent workers.
- [ ] Tenant RLS and repository predicates are tested for every tenant-owned table and operation; missing tenant context fails closed.
- [ ] Leases, budgets, cooldowns, kill switches, and result/audit persistence are transactional or otherwise proven race-safe in an isolated database.
- [ ] The UI displays loading, empty, validation, review, approved, queued, running, stopped, manual-pending, failed, uncertain, session-expired, checkpoint, rate-limited, budget, cooldown, and duplicate states without optimistic false success.
- [ ] Offline, isolated database, controlled browser fixture, typecheck/build, and full test evidence is recorded. Live validation is explicitly recorded only if performed on the approved test account under the approved supervised procedure.

## 9. Test Plan And Evidence Requirements

### Offline tests

- ICP schema defaults, invalid thresholds, hard exclusions, deterministic-before-AI ordering, URL normalization, duplicate imports, review override, and export.
- Post normalization, source provenance, recency/content/blocklist/author/cooldown rules, duplicate post handling, evidence grounding, comment quality, revision invalidation, and review decisions.
- Fake executor like/comment state and audit; Manual executor task creation and explicit completed/failed/uncertain outcomes.
- Queue dispatch for every action type, especially `likePost` and `publishComment`, unsupported action rejection, idempotency replay, approval enforcement, kill switches, cooldowns, and manual fallback.
- Provider malformed output, timeout, rate-limit mapping, safe metadata, and no secret persistence.

### Isolated database tests

- Clean migration and upgrade against PostgreSQL or a separately documented compatible isolated database; do not treat memory-only tests as RLS evidence.
- Two-tenant select/insert/update/delete denial for all tenant-owned tables, including engagement, scheduled actions, leases, budgets, reservations, audit, sessions, evidence, and kill switches.
- Missing tenant context, foreign tenant IDs, and body-supplied tenant/operator/account spoofing fail closed.
- Concurrent semantic duplicate creation, `SKIP LOCKED` action claim, lease replacement/expiry/heartbeat with stale-token rejection, final-budget race, transactional reservation rollback, cooldown race, and terminal-state immutability.
- Migration rollback rehearsal in a disposable database; no production migration or destructive synchronization.

### Controlled browser/test surface

- Use Playwright only in Feature 0.5 test files with local deterministic pages or a controlled test server. Cover session valid, login redirect, profile/post mismatch, already-liked, comment appears, selector version fallback, selector mismatch, checkpoint/CAPTCHA marker, rate-limit marker, navigation/action timeout, browser crash, stop request, cleanup, and redaction.
- Assert no external LinkedIn write occurs in unit/offline tests and that Feature 0.2 does not instantiate `PlaywrightExecutor`.
- Assert visible headed mode for the pilot, one account lease, bounded action count, and captured page-state/evidence hashes.

### Explicit live validation requirements

- Live validation is not claimed by this plan or by automated tests.
- Before any live call, Tushar must approve the authenticated profile/account, data-sharing/provider posture, isolated database, action-specific enablement, limits/cooldowns, compliance posture, and the test account.
- The operator must run one visible, individually approved like, then separately one visible, individually approved comment, with screenshots/log evidence redacted and a manually inspected external result.
- Record actual date, account identifier in redacted form, action type, post identifier in redacted form, browser/selector versions, result, stop behavior, and any uncertainty. If not run, mark live validation `NOT RUN`, not passed.

## 11. Risks, Rollback, And Kill-Switch Procedure

| Risk | Mitigation | Rollback/stop |
| --- | --- | --- |
| Duplicate external like/comment | Semantic idempotency, one lease, atomic claim, post-state verification, no uncertain auto-retry | Disable action type, mark uncertain, reconcile manually; retain audit evidence |
| Wrong target or stale post | Canonical URL/content hash, target identity verification, approval revision binding | Stop account, block action, require new discovery/review |
| Session theft or secret leakage | Persistent profile ownership, encrypted storage/key version, redacted logs/evidence, no credentials in payloads | Disable account, revoke/re-authenticate outside app procedure, preserve sanitized audit |
| LinkedIn checkpoint/CAPTCHA/rate limit | Detect markers, pause account, no bypass, cooldown and human reauthentication | Global/account kill switch; no retry until explicit health reset |
| Budget/cooldown/lease race | DB transactions, row locks, token validation, concurrency tests | Stop worker, reconcile reservations/leases in isolated audited operation |
| Migration or RLS regression | Clean/upgrade/rollback rehearsal and direct two-tenant tests | Disable execution endpoints; use compensating migration only, never reset shared DB |
| Poor or non-grounded comment | Evidence spans, deterministic validator, mandatory separate comment approval | Disable comment capability; preserve draft as rejected/unapproved |
| UI reports false success | Await API result, server refresh, explicit uncertain state and manual fallback | Disable action buttons while state is unresolved; inspect audit |

Emergency procedure: activate global kill switch, stop workers, prevent new claims, allow current browser action to reach a safe checkpoint or close without another write, release only token-valid leases, mark in-flight actions uncertain when external state cannot be verified, and preserve all audit/evidence records. Re-enable only after account health and unresolved actions are manually reviewed.
