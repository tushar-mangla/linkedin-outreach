# RecruitmentOS: ICP to Supervised Engagement Pilot

**Plan ID:** `0.5-recruitmentos-icp-supervised-execution-revised-plan`
**Supersedes:** `docs/plans/0.5-recruitmentos-icp-supervised-execution-gap-plan.md`
**Classification:** Large/risky feature: multi-tenant persistence, external provider data handling, browser-based LinkedIn actions, approvals, budgets, concurrency, and audit evidence.
**Status:** PROPOSED. This plan changes no application code, migrations, tests, or configuration.

## 1. Expected Outcome: Business + User Experience

### Business result

RecruitmentOS will provide an evidence-backed pipeline from an ICP through prospect qualification, post discovery, recommendation drafting, separate human approval, and a supervised action outcome.

**Automated:** deterministic ICP filtering; eligible-post assessment; fake/provider-backed draft generation; validation; queue eligibility evaluation; status/audit recording; simulation; and, only in Feature 0.5 after the action-specific gate, a visible browser attempt.

**Never automated in this scope:** approval of readiness or an action; credential entry or bypassing a LinkedIn checkpoint/CAPTCHA; unattended activity; automatic retry after an uncertain write; scaling beyond the approved pilot; or a claim that an external action occurred without verification evidence.

Likes and comments are independent capabilities. Each needs its own feature flag, approval, action budget, cooldown, kill switch, audit event, browser enablement decision, and completion evidence. The initial pilot processes exactly the Tushar-selected count within **4-5 total posts/actions**, not a presumed daily ceiling. Expansion is refused until the scale-promotion criteria are approved and pilot evidence supports it.

Trustworthy evidence is a tenant-scoped chain from ICP decision through source provenance, post hash, recommendation revision, approval, queue attempt, executor result, and outcome label. Every terminal result must be one of:

- `simulated`: fake executor or fixture-only result; no LinkedIn write was attempted.
- `manual-confirmed`: operator explicitly confirms a manual action with confirmation metadata; this is not independently browser-verified by the product.
- `browser-executed`: the supervised browser completed its write path but external verification is not yet proven; it must not be shown as success.
- `verified`: target and resulting LinkedIn state were explicitly verified and redacted evidence/audit references were persisted.

### Operator UI journey

1. Define an ICP with validated criteria, import prospects, view deterministic and provider qualification evidence, and review prospects into `READY_FOR_CAMPAIGN`.
2. Open a ready prospect, choose fixture/manual post intake for Feature 0.2 or explicitly enabled Feature 0.5 supervised discovery, inspect post text, canonical URL, provenance, recency, content hash, eligibility, and errors.
3. Review campaign readiness separately from engagement. Read generated evidence and validator findings; choose a draft action type (`LIKE` or `COMMENT`) without conflating the two.
4. For a comment, inspect and optionally edit the exact text. Approve, reject, skip author, or pause. An edit creates a new revision and invalidates an earlier approval.
5. See separate Like and Comment feature flags, action budgets, cooldowns, working-hours status, account/session health, queued/running state, pilot count, and kill-switch state before requesting an action.
6. Choose `SIMULATE`, `MANUAL`, or, only after Feature 0.5 enablement, `BROWSER`. The UI obtains server-confirmed action status rather than optimistic local success.
7. Separately approve a like or a comment. The server performs the approval/revision, tenant, readiness, eligibility, cooldown, budget, lease, session/health, and kill-switch checks again before dispatch.
8. Monitor the single visible browser run, see a step/result log, stop safely, and receive explicit handling for login/session expiry, checkpoint/CAPTCHA, selector mismatch, rate limit, timeout, duplicate, or uncertainty.
9. If browser execution is unavailable or blocked, create a durable manual task. The operator records `COMPLETED`, `FAILED`, or `UNCERTAIN`; task creation remains pending, never external success.
10. Inspect the post/action history and final outcome label. Only `verified` is a verified LinkedIn result.

### Required outputs at every stage

| Stage | Required output |
| --- | --- |
| ICP and import | validated criteria, import/batch status, deterministic/provider evidence, prospect stage, review decision, audit event, sanitized errors |
| Readiness | `READY_FOR_CAMPAIGN` or refusal reason; it does not grant engagement approval |
| Discovery/intake | source type, canonical URL, author/prospect association, content hash, publication data, provenance, eligibility, duplicate/cooldown errors, history |
| Recommendation | action type, immutable revision, evidence references, validator findings, provider metadata safe for retention, approval state, audit/history |
| Action request | independently evaluated like/comment flags, budget/cooldown/lease/kill-switch/session result, idempotency result, queue/task status, refusal code |
| Execution | action status, attempt number, executor mode, redacted evidence references, health transition, failure/uncertainty reason, one explicit outcome label |
| Manual fallback | durable task status, confirmation actor/time/metadata, `manual-confirmed` only after explicit terminal outcome |

### Binary completion contract

This feature is complete only when all acceptance criteria in Section 10 are true and recorded evidence distinguishes simulation, manual confirmation, browser completion, and verified result. The implementation must refuse or label unsupported:

- any unapproved, stale, cross-tenant, not-ready, ineligible, duplicate, cooldown-blocked, budget-blocked, lease-invalid, kill-switched, paused, session-expired, checkpointed, or uncertain action;
- browser writes when the separate action flag or Feature 0.5 gate is disabled;
- unattended runs, CAPTCHA/checkpoint circumvention, credential capture/storage in action payloads or audit logs, and automatic uncertainty retries;
- daily-limit or scale claims not separately approved; and
- a live LinkedIn success claim where the only evidence is a queue completion, browser click, or operator assumption.

## 2. Scope, Assumptions, and Boundaries

### Goal

Deliver a controlled Small Group -> Automation capability: qualify ICP prospects, prepare/post-review engagement, independently authorize likes and comments, simulate or manually confirm actions, and prepare a supervised Feature 0.5 browser pilot with durable controls and evidence.

### Assumptions

- `APPROVED_DEV_DATABASE_TARGET` is the only approved development PostgreSQL target. This plan does not reproduce or store its sensitive connection details.
- Authenticated LinkedIn browser-profile use is approved only for supervised development/testing, not unattended use.
- Sending post content to Gemini, Luna, or another selected provider is approved in principle; retention, minimization, and provider-specific policy remain approval decisions.
- The current deployment is single-user, but the server must derive trusted tenant/operator context and retain tenant isolation.
- Feature 0.2 stays preparation-first. Fixture/manual discovery and Fake/Manual execution remain usable without a browser. Live browser writes are exclusively supervised Feature 0.5 work.

### Non-goals

- Connections, messages, follow-ups, campaigns/sequences, profile edits, reply automation, analytics, stealth behavior, multi-account execution, and automatic scale-up.
- Legal advice or a statement that browser behavior is platform-compliant.
- Environment/credential/MCP configuration changes.

## 5. Entities, Permissions, Contracts, and State

### Required entities and constraints

| Entity | Required contract |
| --- | --- |
| ICP/prospect/evaluation/review | Preserve current pipeline. Readiness and engagement approval are different states. Tenant-scoped uniqueness for normalized LinkedIn profile remains. |
| Engagement post | tenant, prospect, canonical post URL, author identity, normalized text, published time, source/provenance, content hash, eligibility decision/reasons; unique `(tenant_id, canonical_post_url)`. |
| Recommendation revision and approval | action type, post hash, immutable text/evidence revision, validation report, provider-safe metadata, revision state, actor/time/reason. Approval binds exactly one revision and expires/supersedes on change. |
| Author/prospect controls and cooldown | separate action-type scope, author/prospect/account scope, start/end/reason/result. Like and comment policy values are independent. |
| Scheduled action/idempotency | tenant, account, recommendation revision, action type, payload hash, idempotency key scoped to semantic request, status/claim timestamps. One semantic action may make at most one uncertain/live external attempt. |
| Manual task/action result | durable task `PENDING_CONFIRMATION`, terminal result, operator confirmation, executor mode, outcome label, verification/evidence reference; task creation is not success. |
| Budget/lease | action-specific account/day budget plus reservation in a transaction; token-bound lease with heartbeat, expiry, claim/release validation. |
| Browser account/session/health | account/session metadata and key version only, never raw credentials; `HEALTHY`, `WARNING`, `PAUSED`, `CHECKPOINT_DETECTED`, `REAUTH_REQUIRED`, `DISABLED`. |
| Kill switch/evidence/audit | global/tenant/account/action-type kill switch, immutable actor/reason/timestamp history, redacted page/evidence hashes and selector version. |

### Authorization and API contract

The server derives tenant and operator from trusted context, never from request bodies. Every command verifies tenant ownership plus prospect readiness, post eligibility, current revision, action-specific approval, independent flag, cooldown/budget, lease, health/session, and kill-switch state.

Preserve existing ICP/import/prospect/export routes. Proposed additive API surface:

- `POST /api/engagement/scan`: Feature 0.2 fixture/manual source by default; Feature 0.5 browser discovery requires explicit capability state.
- `GET /api/engagement/posts`, `GET /api/engagement/recommendations`, and decision routes return provenance, eligibility, revision, approval, validation, status, and redacted error data.
- `POST /api/engagement/recommendations/:id/actions`: `{ actionType, accountId, mode: 'SIMULATE' | 'MANUAL' | 'BROWSER', idempotencyKey }`; the server rejects client-supplied tenant/operator authorization and returns existing action on idempotent replay.
- `POST /api/manual-tasks/:id/outcome`: explicit terminal outcome plus confirmation metadata; conflicts on terminal task.
- Feature 0.5-only account/session/run/stop/kill-switch/audit routes return no cookies, profile directory, credential, or provider secret data.

Use machine-readable errors including `PROSPECT_NOT_READY`, `POST_NOT_ELIGIBLE`, `APPROVAL_REQUIRED`, `APPROVAL_STALE`, `ACTION_DUPLICATE`, `COOLDOWN_ACTIVE`, `BUDGET_EXCEEDED`, `LEASE_UNAVAILABLE`, `KILL_SWITCH_ACTIVE`, `ACCOUNT_PAUSED`, `SESSION_EXPIRED`, `CHECKPOINT_DETECTED`, `SELECTOR_MISMATCH`, `RATE_LIMITED`, `EXECUTION_TIMEOUT`, `EXECUTION_FAILED`, `EXECUTION_UNCERTAIN`, `MANUAL_CONFIRMATION_PENDING`, and `PROVIDER_UNAVAILABLE`.

### Frontend contract

The partial React UI must replace demo-only state with API-backed ICP, prospect, post, recommendation, approval, action, health, and audit data. It must render loading, empty, validation, eligibility/refusal, edited/stale approval, budget/cooldown, disabled flag, queued/running/stopped, manual-pending, failed, uncertain, session-expired, checkpoint, rate-limit, and verified states. It must not imply that an action ran before a confirmed server response.

## 8. Pilot Behavior and Operational Posture

### Conservative pilot

- Select the exact pilot count within 4-5 total posts/actions before execution; do not invent a final daily threshold.
- Execute one action at a time on one approved account with a visible browser and a valid lease.
- Independently enable Like and Comment. A successful like pilot does not enable comments.
- Stop immediately on checkpoint/CAPTCHA, session expiry, rate limit, unexpected page state, selector mismatch, timeout, browser crash, user stop, or uncertain result. Do not automatically retry any potentially written action.
- Record `simulated`, `manual-confirmed`, `browser-executed`, or `verified`; no other success shorthand may conceal verification status.

### Plain-language compliance and operational posture

Browser-based LinkedIn activity can conflict with platform terms or policy and can create account-safety risk. This plan does not provide legal advice and does not claim compliance. The safe operating posture is to use a personally controlled authenticated profile only with human oversight, keep each action individually approved, respect visible platform controls, avoid CAPTCHA/checkpoint evasion, minimize sent/provider-retained post data, use conservative pacing and approved working hours, keep an auditable record, and stop promptly through action/account/global kill switches. Approvals matter because they make a human responsible for the target, the content, the action type, and the decision to proceed in a context where automation cannot safely infer intent or platform permission.

## 10. Acceptance Criteria and Test Plan

### Binary acceptance criteria

- [ ] ICP criteria are validated, imports are qualified deterministically before providers, evidence/history is tenant-scoped, and only an explicit review can make a prospect `READY_FOR_CAMPAIGN`.
- [ ] A ready prospect can receive fixture/manual discovery in Feature 0.2 and, only under Feature 0.5 enablement, supervised discovery with canonical URL, source, hash, eligibility, audit/history, and sanitized failures.
- [ ] Drafts are evidence-grounded, validation findings are visible, revisions are immutable, editing invalidates approval, and readiness is never treated as action approval.
- [ ] Like and Comment each have independent flag, approval, budget, cooldown, kill switch, queue dispatch, UI state, audit record, and test coverage.
- [ ] Fake action produces only `simulated`; manual task creation produces pending state; explicit manual outcome produces only `manual-confirmed`; browser action is never called verified without external-state verification.
- [ ] No duplicate action/external attempt can arise from API replay, concurrent workers, retry, restart, or stale approval. An existing idempotent action is returned rather than recreated.
- [ ] Budget exhaustion, cooldown, invalid/expired lease, kill switch, failed health/session check, rate limit, timeout, selector mismatch, checkpoint/CAPTCHA, and browser crash yield durable non-success state and no unsafe retry.
- [ ] Session expiry pauses the account, requires explicit reauthentication/session verification, and blocks dispatch until reset by an authorized operator.
- [ ] All tenant-owned state is RLS protected and repository-scoped; missing/foreign tenant context fails closed.
- [ ] The selected 4-5 action pilot is separately approved, visible, one-at-a-time, and recorded with verified/uncertain labels; no scale claim is made from simulation alone.

### Offline tests

- Unit tests for ICP validation/filter order, post normalization/eligibility, author controls, comment validator, revision invalidation, provider malformed/timeout/error behavior, error mapping, independent like/comment controls, fake/manual outcomes, audit redaction, and duplicate prevention.
- Queue tests for every action type, especially `likePost` and `publishComment`, with approval/safety gate, idempotency, cooldown, budget, lease, kill switch, failure, and uncertainty behavior.
- API/UI tests for server-derived tenant/operator, response states, no optimistic review/action success, manual confirmation, and all failure/empty/loading states.

### Isolated database tests

- Run migrations and database/RLS/concurrency tests only after explicit migration/run approval, and only against `APPROVED_DEV_DATABASE_TARGET` or an explicitly approved isolated equivalent.
- Verify clean install and current-chain upgrade, RLS select/insert/update/delete denial, missing tenant failure, atomic duplicate action creation, `SKIP LOCKED` claim, stale-token lease rejection, budget reservation rollback, cooldown race, terminal-state transition refusal, and compensating rollback rehearsal.
- Do not use memory doubles as evidence of PostgreSQL RLS, transactional claims, or migration safety.

### Controlled browser and live validation

- Controlled local fixture tests cover valid session, login redirect, wrong post, already-liked, visible comment result, selector mismatch, checkpoint/CAPTCHA marker, rate-limit marker, timeout, crash, stop, cleanup, and redaction. No external LinkedIn write occurs in automated tests.
- Live LinkedIn validation is **NOT RUN** unless specifically executed. It requires the approved account/profile, selected provider data policy, action-type flag, exact pilot count, working hours, retry/manual-fallback policy, and the separate migration/run authorization where applicable.
- For every pilot action, record redacted account/post identifiers, approval revision, browser/selector version, observed status, evidence hash, stop behavior, final outcome label, and manual inspection. A browser click without verified external state remains `browser-executed` or `EXECUTION_UNCERTAIN`, not `verified`.

## 11. Risks, Rollback, and Kill Switch

| Risk | Mitigation and rollback |
| --- | --- |
| Duplicate or wrong-target action | revision/hash binding, semantic idempotency, one lease, target verification; disable action type, mark uncertain, reconcile manually. |
| Account/platform risk | human oversight, visible browser, conservative pilot, no bypass, stop on checkpoint/rate limit; pause account/global kill switch. |
| Session/credential exposure | controlled session owner, no secret payload/audit logging, redaction; disable account and reauthenticate outside application logic. |
| Provider privacy/cost/failure | fake default, minimum data, output validation, retention decision; disable provider and leave drafts unapproved. |
| Database/RLS/migration regression | forward migration, isolated tests, compensating migration; disable execution routes before data-changing rollback. |
| False UI success | server-confirmed mutations, explicit outcome labels, audit lookup; disable action controls while status is unresolved. |

Emergency procedure: activate the global kill switch, stop worker/browser at the next safe checkpoint without another write, prevent claims, mark unverifiable in-flight action `UNCERTAIN`, pause affected account, preserve redacted evidence/audit data, then require manual review before re-enablement.
