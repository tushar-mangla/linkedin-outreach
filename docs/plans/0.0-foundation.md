# Feature 0: Core Foundation
**Release:** `v0.0-foundation`

## Intention
Establish the multi-tenant persistence and operational controls required for every later workflow. This release performs no live LinkedIn activity and does not qualify or contact prospects.

## User Outcome
An operator can create test tenant data, schedule simulated actions, process them through FakeExecutor or ManualExecutor, enforce account budgets and leases, and inspect a persistent audit trail without cross-tenant access.

## Scope
- Tenant, user, LinkedIn account, and browser-session boundary models.
- Tenant context, tenant-scoped repositories, and PostgreSQL RLS.
- Campaign, sequence, enrollment, scheduled-action, approval, and audit foundations needed by later releases.
- Account leases with ownership tokens, expiry, heartbeat, and recovery.
- Atomic per-account, per-action daily budget reservations.
- FakeExecutor and ManualExecutor contracts.
- Persistent audit events with correlation IDs and payload hashes.
- Kill-switch and account-health fields, without live browser execution.

## Domain States
Keep qualification, readiness, engagement eligibility, enrollment, action, approval, and account health as separate status dimensions. Use the shared vocabulary defined by the canonical product plan; do not introduce a generic status field that combines them.

## Contracts
- `LinkedInExecutor` supports visit, like, comment, connection, message, connection checks, and reply checks with explicit success and uncertainty results.
- `AIProvider` is defined for later releases; Feature 0 supplies only fake/test boundaries.
- All tenant-owned records include `tenant_id`.
- Every scheduled action has an idempotency key and cannot execute without approval, a valid account lease, and a budget reservation where required.

## Persistence and Migrations
Use Drizzle schema definitions and reviewed PostgreSQL migrations. Add foreign keys and tenant indexes. RLS must cover every tenant-owned table, including leases and future action tables, and must be set transaction-locally from validated tenant context. Never use a shared process-global tenant placeholder.

## Implementation Boundaries
Business services depend on repositories and executor interfaces. They do not call Playwright, raw browser APIs, or external LinkedIn services. Audit writes belong to the persistence boundary rather than an in-memory logger.

## Tests
- Fresh migration against PostgreSQL.
- Repository and database RLS isolation across two tenants.
- Missing tenant context fails closed.
- Two workers cannot hold one account lease.
- Expired leases recover; stale lease tokens cannot execute or release another worker's lease.
- Only one worker reserves the last budget unit.
- Action claiming is locked and idempotent.
- Uncertain actions are not automatically retried.
- Fake and Manual executor outcomes create persistent audit events.
- Typecheck, build, and the full test suite pass.

## Offline Demonstration
Use local PostgreSQL, FakeExecutor, and ManualExecutor to create two tenants, schedule approved actions, process one action, demonstrate budget and lease denial, recover an expired lease, and inspect the audit history.

## Human Approval
The project lead approves the schema, RLS policy, lease and budget semantics, audit retention, executor contract, and offline demonstration before Feature 1 implementation begins.

## Release Gate
Feature 0 is complete only when all persistence, isolation, concurrency, recovery, audit, and offline criteria pass. The release tag is `v0.0-foundation`.
