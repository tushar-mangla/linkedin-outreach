# Feature 2: Engagement Native Integration - Evidence-Backed Implementation Plan

**Release:** `v0.2-engagement`  
**Classification:** Feature planning, large/risky: persistence, authorization, AI providers, scheduling concurrency, and an external-execution boundary.  
**Plan status:** Proposed; no application code is changed by this plan.

## 1. Goal And Business Outcome

Enable a recruiter to turn an ICP-approved prospect's recent, supplied LinkedIn post into a safe, evidence-grounded engagement recommendation, approve or edit it, and complete it through an offline Fake or Manual executor with durable audit evidence. The outcome is credible recruiter engagement preparation with no live LinkedIn scanning or browser publishing in this release.

The first implementation increment delivers this end-to-end offline outcome for one post at a time. Later slices extend it only after the first increment passes its acceptance and evidence gates.

## 3. Assumptions, Scope, And Non-Goals

### Assumptions

1. A prospect must be tenant-owned and in `READY_FOR_CAMPAIGN` before it can receive engagement eligibility or recommendations.
2. Feature 2 consumes manual or fixture post content and URLs. It never scrapes, scans, authenticates to, or writes to LinkedIn.
3. The authenticated deployment is currently single-user, but all Feature 2 records retain `tenant_id` and operator identity so the multi-tenant contract remains enforceable.
4. A recommendation is an advisory object; qualification, engagement eligibility, approval, scheduled-action status, and execution result remain independent state dimensions.
5. First increment execution is Fake or Manual only. A Manual completion needs an explicit operator confirmation; task creation alone is not external-action success.

### In scope

- Advisory profile audit from manually submitted structured profile facts.
- Fixture/manual post intake, validation, provenance, filtering, cooldown, recommendation generation, validation, approval/edit/reject/pause/skip-author decisions, and offline execution.
- Tenant-scoped persistence, auditable state changes, API contracts, React screens, and offline end-to-end verification.
- Feature 0 remediation needed to make Feature 2 action scheduling honest and safe.

### Non-goals

- Live LinkedIn feed discovery, scraping, authentication, profile edits, browser execution, unattended publishing, or production external writes.
- Message, connection, sequence, reply-stop, or KPI functionality belonging to Features 3-6.
- New tool/MCP setup, environment-variable changes, or a provider rollout without separate approval.

## 4. User Journeys

### Primary recruiter journey: first increment

1. Recruiter opens a campaign-ready prospect and selects **Engagement**.
2. Recruiter submits or selects a supplied post fixture/manual record with the post URL, author profile URL, text, publication time, and provenance.
3. System validates URL/content/tenant ownership, rejects duplicates and blocked/expired/low-quality content, and records a transparent eligibility decision.
4. Recruiter requests a recommendation. Deterministic rules run before any provider. A fake provider produces an evidence-cited structured recommendation; the quality validator rejects generic, invented, sales-oriented, duplicated, or evidence-free comments.
5. Recruiter reviews evidence, original text, generated text, validation findings, and policy/cooldown status. They approve the original, save an edited version, reject it, pause the prospect, or skip the author.
6. Only an approved, still-current recommendation may create an offline action. The service rechecks tenant, prospect readiness, recommendation state/version, blocklist/cooldown, account lease, and independent action budget.
7. Fake execution records a deterministic result. Manual execution creates a durable task, then the recruiter explicitly records a completed, failed, or uncertain outcome.
8. UI shows the result and immutable audit trail; uncertain results are not retried automatically.

### Negative/edge journeys

- A non-ready, foreign-tenant, paused, or skipped prospect cannot request/approve/schedule engagement.
- A stale approval (content changed after approval), duplicate post/action key, expired post, cooldown conflict, budget exhaustion, invalid lease, provider timeout, malformed provider output, or quality rejection produces an actionable error and no action is executed.
- Two workers racing to execute the last permitted action cause exactly one successful claim/reservation; the other receives a deterministic denial.

## 5. Domain Model, Permissions, And Contracts

### Entities and independent state machines

| Entity | Required state/fields | Permission and invariant |
| --- | --- | --- |
| `profile_audit_reports` | advisory score/findings/version, source snapshot/hash | Any authorized recruiter can create/view tenant report; never writes LinkedIn profile. |
| `engagement_posts` | prospect/author IDs, canonical post URL, text/media summary, occurred time, provenance/source, content hash, eligibility result | Unique per tenant/canonical URL; source data immutable after intake. |
| `engagement_author_controls` | tenant/prospect/author key, `ACTIVE`/`SKIPPED`/`BLOCKED`, reason, actor, expiry | Skip/block prevents new recommendations and scheduling. |
| `engagement_recommendations` | post/prospect, action `LIKE`/`COMMENT`, evidence refs, generated draft, provider metadata, validation report, revision, status | Cannot be scheduled unless current approved revision validates. |
| `engagement_approvals` | recommendation/revision, `PENDING`/`APPROVED`/`REJECTED`/`SUPERSEDED`, actor/reason/time | Approval authorizes only immutable recommendation revision; content edit supersedes approval. |
| `engagement_cooldowns` | tenant/account/prospect/author/action scope, starts/ends, origin/result | Scope and duration must be independently enforced, not inferred from budget. |
| `manual_execution_tasks` | scheduled action/recommendation, instructions, status, operator outcome, timestamps | Task creation is `PENDING_CONFIRMATION`; completion must be explicit. |
| `scheduled_actions` | existing action lifecycle plus engagement payload/recommendation reference | One terminal action per approved recommendation/revision; idempotency key must be tenant-scoped and semantic. |

### Authorization model

Until role-based access control exists, server derives a trusted local operator identity and tenant context; it must never accept an arbitrary `operatorId` or `tenantId` from the body. Every command additionally confirms the prospect/post/recommendation belongs to the active tenant.

Required authorization decisions:

- `READY_FOR_CAMPAIGN` is necessary but not sufficient for engagement.
- `PAUSED`, `SKIPPED`, `BLOCKED`, post ineligibility, missing approval, superseded approval, validation failure, and stale content block scheduling.
- Approving prospect readiness does not approve an engagement recommendation.
- An approval is tied to the exact recommendation revision/content hash. Editing creates a new revision and invalidates old approval.
- Dispatch rechecks approval and all safety predicates under the transaction/claim boundary; UI approval is never authorization by itself.

### HTTP API contract (first increment)

All JSON request bodies use Zod at the route boundary. Responses return RFC-appropriate JSON `{ error: { code, message, details? } }` errors; no provider stack/error secrets are returned.

| Endpoint | Request/response | Validation/error behavior |
| --- | --- | --- |
| `POST /api/prospects/:prospectId/profile-audits` | Structured sender profile snapshot; returns report | `404` foreign/missing prospect, `409` paused/not-ready, `422` invalid profile fields. |
| `GET /api/prospects/:prospectId/engagement/posts` | List post records plus eligibility | `404` foreign/missing; no raw cross-tenant data. |
| `POST /api/prospects/:prospectId/engagement/posts` | Manual post input; returns stored post + decision | `422` malformed/unsupported content; `409` duplicate URL/hash, cooldown or author control. |
| `POST /api/engagement/posts/:postId/recommendations` | `{ actionType }`; returns validated recommendation or review-required result | `409` not eligible; `422` policy/quality failure; `503` provider unavailable/timeout. |
| `GET /api/engagement/recommendations` | Filter by status/prospect with bounded pagination | Tenant-scoped results only. |
| `POST /api/engagement/recommendations/:id/decision` | `APPROVE`, `REJECT`, `PAUSE_PROSPECT`, `SKIP_AUTHOR`, or `EDIT_AND_APPROVE`, reason/edit as needed | `409` stale revision/terminal decision; `422` invalid edit/policy failure. |
| `POST /api/engagement/recommendations/:id/actions` | `{ accountId, mode: 'FAKE' | 'MANUAL', idempotencyKey }`; returns queued action/task | `403` not approved/authorized; `409` duplicate/stale/cooldown; `429` budget exhausted; `503` lease unavailable. |
| `POST /api/manual-tasks/:id/outcome` | `COMPLETED`, `FAILED`, or `UNCERTAIN` plus confirmation metadata | `409` already terminal; uncertain never reschedules automatically. |
| `GET /api/engagement/audit` | Bounded filtered history | Tenant-scoped immutable audit records. |

### Post source interface

Create `PostSourceAdapter` separately from `ProspectSourceAdapter`:

```ts
interface PostSourceAdapter<Input> {
  validate(input: Input): Promise<PostIngestionResult>;
  ingest(input: Input): Promise<NormalizedEngagementPost[]>;
}
```

Required adapters for Feature 2: `FixturePostSourceAdapter` for deterministic tests/demo and `ManualPostSourceAdapter` for API input. Both must preserve source type, received timestamp, original payload hash, canonical post URL, and evidence snippet. A future live LinkedIn adapter must be a separate Feature 5 proposal; it must not be a hidden implementation of this interface in Feature 2.

### Provider interface and `codex-everywhere` / `luna` handling

Use a new engagement-specific interface instead of expanding `ICPModelProvider`, whose only implemented method is `evaluate`:

```ts
interface EngagementGenerationProvider {
  generateRecommendation(input: EngagementGenerationInput): Promise<EngagementGenerationOutput>;
}
```

The input includes only normalized post evidence, policy version, max length, prohibited-pattern rules, provider timeout, and correlation ID. Output must include structured action type, draft, cited evidence spans, provider/model/prompt/schema versions, usage metadata, and provider request ID when safely available.

- `FakeEngagementProvider` is REQUIRED for all automated tests and offline demo.
- A `GeminiEngagementProvider` is PROPOSED only after a current SDK/documentation review and retains the existing provider's lessons: bounded timeout, retry only before a response is accepted, Zod validation, and sanitized failures.
- `CodexEverywhereEngagementProvider` and `LunaEngagementProvider` are DEFERRED/PROPOSED. No package/configuration exists today. Implement at most one after Tushar selects the official supported integration method and approves the data-sharing/privacy posture.
- Provider failures map to durable `PROVIDER_UNAVAILABLE`, `PROVIDER_TIMEOUT`, `PROVIDER_MALFORMED_OUTPUT`, or `PROVIDER_POLICY_REJECTED` states; they do not create an approval or scheduled action. Store safe metadata and hashes, never credentials, raw authorization headers, or secrets.
- Provider outputs are treated as untrusted until `EngagementRecommendationSchema` and deterministic quality validation pass.

## 6. Schema And Migration Approach

### Schema decisions

1. Add additive, forward-only Drizzle tables and matching TypeScript domain types. Do not repurpose `review_decisions`, which is prospect-readiness-specific.
2. Use `uuid` keys and explicit `tenant_id` on every tenant-owned Feature 2 table, including any manual task and cooldown record.
3. Store flexible evidence/validation/provider metadata in JSON only where it is audit/provenance payload; retain queryable state, keys, timestamps, hashes, and foreign keys as first-class columns.
4. Normalize post URL and author profile URL before insert. Add unique indexes such as `(tenant_id, canonical_post_url)` and a semantic one-action-per-recommendation/revision constraint.
5. Define deterministic, UTC cooldown comparison semantics, with `ends_at > now()` and index the safety lookup `(tenant_id, account_id, author_key, action_type, ends_at)` plus prospect scope as needed.
6. Expand `scheduled_actions` with a nullable engagement recommendation FK only after all existing migration snapshots and generated SQL are reconciled. Generate idempotency keys from tenant, account, recommendation ID, revision, action type, and executor mode; add a database constraint with the intended tenancy scope rather than relying on UI de-duplication.
7. Add check constraints where PostgreSQL supports them: non-empty URLs/text as appropriate, valid enum/status values, `ends_at > starts_at`, completed/failed/uncertain timestamps for terminal manual tasks, and bounded action type values.

### Migration sequence

1. First reconcile migration drift: `src/db/schema.ts` has `APPROVED_FOR_OUTREACH`, lease token/heartbeat, campaign, sequence, enrollment, and scheduled-action definitions that are absent from migrations `0000`-`0002`; do not generate Feature 2 SQL on top of unexplained drift.
2. Prepare a reviewed additive reconciliation migration with no destructive `db:push`; verify it applies to a clean PostgreSQL database and the existing local migration chain.
3. Add Feature 2 tables/indexes/foreign keys as a separate reviewed migration and regenerate `drizzle/meta` snapshots through the repository's supported generation command.
4. Extend RLS policy and `FORCE ROW LEVEL SECURITY` to every existing and new tenant-owned table; use both `USING` and `WITH CHECK` policies and tenant context set within every transaction.
5. Backfill nothing for Feature 2. Existing ready prospects remain eligible to receive posts only when explicitly supplied; there is no implicit historic post migration.
6. Validate forward migration on an empty and representative development database, then validate rollback by applying a compensating migration in an isolated database. No production migration occurs without separate explicit approval.

**Scope:** Implement decision commands and immutable approval/revision records; make edited approved content a new revision; add pause prospect and skip author controls; audit all decisions.

**Scope:** Wire `like` and `comment` queue dispatch to existing Fake/Manual executor methods; persist manual tasks/outcomes; check approval, cooldown, budget, idempotency, and lease independently before dispatch; record result and audit correlation.

## 9. Validation, Error States, And Acceptance Criteria

### Validators

- Canonical post URL must be HTTPS LinkedIn post URL under the approved source policy; malformed/unknown URLs are rejected, never normalized to a sentinel.
- Manual post text has non-empty and configured maximum length; publication time is a valid timestamp; author profile key must be canonicalizable.
- Action type is exactly `LIKE` or `COMMENT`; comments have configured min/max length and cannot be blank after normalization.
- Evidence citations must resolve to verbatim stored spans from the specific post. The comment cannot state a claim absent from those spans.
- Explicit policy checks reject phrase repetition against prior author/prospect comments, generic praise-only language, CTA/sales pitches, prohibited content, unapproved URLs, and unsupported assertions.
- Approval decision requires a reason for rejection/pause/skip and a revision/content hash for approval. Manual outcome requires a terminal result and operator confirmation metadata.

### Error state contract

| Error code | HTTP class | UI behavior | State mutation |
| --- | --- | --- | --- |
| `PROSPECT_NOT_READY`, `PROSPECT_PAUSED`, `AUTHOR_SKIPPED`, `POST_NOT_ELIGIBLE` | 409 | Explain blocking policy and link/display next valid state | None except explicit pause/skip decision. |
| `POST_DUPLICATE`, `ACTION_DUPLICATE`, `APPROVAL_STALE` | 409 | Show existing record/status; prevent duplicate buttons | None. |
| `VALIDATION_FAILED`, `COMMENT_POLICY_REJECTED` | 422 | Inline field/findings with no retry side effect | Draft may be retained as unapproved only. |
| `APPROVAL_REQUIRED`, `TENANT_ACCESS_DENIED` | 403 | Non-disclosing access/safety message | None. |
| `COOLDOWN_ACTIVE`, `BUDGET_EXCEEDED`, `LEASE_UNAVAILABLE` | 409/429/503 as specified | Display remaining time or retry guidance without creating an action | No external dispatch. |
| `PROVIDER_TIMEOUT`, `PROVIDER_UNAVAILABLE`, `PROVIDER_MALFORMED_OUTPUT` | 503/422 | Preserve intake context; allow an explicit later regenerate action | No approval/action. |
| `MANUAL_CONFIRMATION_PENDING` | 202 | Display task/instructions and pending status | Task persists only. |
| `EXECUTION_FAILED`, `EXECUTION_UNCERTAIN` | 409/202 | Display auditable terminal result; no automatic retry for uncertain | Persist result and release/commit budget according to policy. |

### Binary completion contract

Feature 2 is **complete** only when every statement below is true:

- [ ] A campaign-ready tenant prospect can receive a manually/fixture-supplied post, get an explainable eligibility decision, generate a validated evidence-grounded like/comment recommendation through the fake provider, approve/edit/reject it, complete it through Fake or Manual mode, and view durable provenance/audit history.
- [ ] No unapproved, stale, invalid, duplicate, cooldown-blocked, paused, skipped, cross-tenant, lease-invalid, or budget-exhausted engagement action can dispatch.
- [ ] Like/comment queue dispatch works through the existing `LinkedInExecutor` interface and Fake/Manual implementations; Feature 2 includes no Playwright or live LinkedIn write.
- [ ] PostgreSQL migrations apply cleanly from an empty database and over the current migration chain, RLS is tested for all tenant-owned Feature 2 and prerequisite tables, and migration/schema drift is resolved.
- [ ] Automated tests cover required unit, persistence, API, and offline journey cases; typecheck, build, full test suite, and human-reviewed offline demo pass.
- [ ] Tushar explicitly approves provider choice/policy and release demonstration after reviewing the evidence.

Any unchecked item means Feature 2 remains incomplete.

## 10. Test And Verification Plan

### Unit tests

- Post URL normalization, source validation, profile audit scoring, eligibility/recency/blocklist rules, author key derivation, duplicate detection, and all cooldown scopes.
- Quality validator acceptance/rejection cases: evidence spans, factual grounding, generic praise, sales pitch, repeated comment, prohibited phrase, empty/over-limit content, and edited content.
- Provider fake success, malformed output, timeout, retry behavior before acceptance, safe failure mapping, metadata preservation, and no secret persistence.
- Approval revision invalidation, pause, skip, reject, and state-transition refusal cases.

### Database/persistence tests (real PostgreSQL/PGlite only where semantics match)

- Unique post/action/idempotency constraints, FK integrity, canonical URL collisions, and terminal-state immutability.
- Two-tenant RLS denial tests for every new and prerequisite tenant-owned table, including direct selects/inserts/updates and missing tenant context fail-closed behavior.
- Concurrent duplicate recommendation/action submission, concurrent claim, final-budget race, reservation-insert rollback, token-stale lease release/heartbeat/dispatch, and cooldown race.
- Migration clean install, existing-chain upgrade, and isolated rollback rehearsal.

### API tests

- Request/response schemas, trusted tenant/operator identity, all success responses, every error code in the error-state table, pagination/filter bounds, and no internal provider error leakage.
- Authorization that verifies prospect ownership/readiness at every command, not merely on list endpoints.

### UI tests

- Component/browser-level tests for post intake, rationale visibility, review/editor, approval invalidation after edit, and all loading/error/empty/pending/terminal states.
- No current automated browser runner exists. Add UI tests only after selecting a supported harness; Feature 2 must not add Playwright or browser automation because that is Feature 5. The allowable boundary test is static/contract-level confirmation that Feature 2 imports no Playwright executor.

### Offline end-to-end demo

Use fixture data for one ready prospect and two posts: one eligible and one blocked. Audit profile; ingest posts; generate one fake recommendation; edit/approve it; execute Fake; generate/approve one Manual recommendation; explicitly record its manual completion; then show audit records, cooldown preventing a duplicate, and a blocked cross-tenant attempt. Run without provider credentials, browser, or LinkedIn access.

### Required verification commands after implementation

Run `npm run typecheck`, `npm test`, `npm run build`, focused engagement/API/persistence tests, a clean migration application through `npm run db:migrate` against an approved non-production database, and the documented offline demonstration. Record exact results in the implementation handoff; this planning turn could not execute the first three due to shell permissions.

## 12. Risks And Rollback

| Risk | Mitigation | Rollback notes |
| --- | --- | --- |
| Feature 0/1 safety claims exceed actual PostgreSQL implementation | Make Slice 0 acceptance a release prerequisite and test real DB semantics. | Do not enable engagement scheduling; retain read-only intake/recommendation work until fixed. |
| Incorrect generation creates poor or unsupported comments | Deterministic evidence/quality validator, mandatory human approval, fake-first release. | Disable provider/recommendation endpoint; retained drafts remain unapproved and never dispatch. |
| Double action from race/retry | Database uniqueness, atomic claim, semantic idempotency, approved revision binding, cooldown, and terminal result records. | Mark action uncertain, stop retries, reconcile manually; do not delete audit evidence. |
| Budget/cooldown leakage on partial failure | Transactional reservation workflow and explicit reservation/result transitions. | Release only verified open reservations through an audited reconciliation command; no counter edits by hand. |
| Cross-tenant disclosure | RLS coverage plus tenant-scoped repository commands and direct DB tests. | Disable affected endpoints and revoke/rotate access outside this feature scope; investigate audit records. |
| Provider privacy, cost, or vendor lock-in | Provider boundary, fake default, explicit provider selection and data-policy review. | Swap selected adapter to fake/disabled; preserve provider-neutral stored evidence and recommendation revisions. |
| Migration failure | Additive reviewed migrations, clean/upgrade rehearsals, backup/restore procedure per deployment. | Use a forward compensating migration; do not destructive-reset shared data. |
| Premature browser automation | No Playwright dependency/executor in Feature 2, contract boundary tests, Feature 5 gate. | Feature 2 contains no live action to roll back. |

## 13. Decisions Requiring Tushar Approval

1. Confirm that Feature 2 must first remediate the identified Feature 0/1 PostgreSQL approval, RLS, queue, lease, and migration gaps rather than treating existing memory tests as sufficient.
2. Approve eligibility policy values: recency window, allowed post formats, quality thresholds, blocklist sources, same-author/prospect cooldown durations, and whether `LIKE` has a separate lower budget/cooldown from `COMMENT`.
3. Approve who may create/approve/reject/pause/skip/manual-confirm in the current single-user deployment and the desired future role names before API claims them.
4. Approve whether profile audit is stored as a versioned report per prospect, per sender profile, or both; the first increment recommends tenant-level sender profile snapshot plus prospect-targeted report linkage.
5. Select exactly one engagement generation provider for a later adapter: retain fake-only initially, Gemini, `codex-everywhere`, or `luna`. `codex-everywhere` and `luna` cannot be assumed available because no repository evidence exists.
6. Approve provider data-sharing, retention, model/version pinning, timeout/retry budget, and safe telemetry policy before a non-fake provider is enabled.
7. Confirm whether the first release includes API-backed React UI (recommended) or is backend/offline demo only; this plan scopes UI into first increment because the stated user workflow requires review and approval UX.
8. Confirm that Playwright remains Feature 5 only. Any request to move browser execution into Feature 2 is a material plan change requiring a new review.

## 14. Definition Of Done And Release Gate

The release gate is passed only when the binary completion contract is fully checked, the full verification plan records passing evidence, the Feature 0 remediation prerequisite has passed with real database evidence, the offline end-to-end demonstration is reviewed, and Tushar approves the policy/provider decisions. The release remains simulation-first: no browser session, live LinkedIn activity, or unattended external publication is part of `v0.2-engagement`.
